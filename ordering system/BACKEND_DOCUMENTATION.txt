1. SYSTEM OVERVIEW
================================================================================

The Ordering System Backend is built with:
- Language: PHP 8.2.12
- Database: MySQL 5.7+
- Server: Apache 2.4.58
- Authentication: Session-based with BCrypt hashing
- Architecture: MVC-style with role-based access control

Three User Types:
- CUSTOMER: Browse products, shop, track loyalty points
- PRODUCER: Manage products, stock, and view orders
- ADMIN: Approve/manage producers, system oversight


2. DATABASE SCHEMA
================================================================================

TABLE: products
- id (INT, Primary Key, Auto Increment)
- name (VARCHAR 100)
- price (DECIMAL 10,2)
- image (VARCHAR 255)
- stock (INT, default: 100)
- producer_id (INT, Foreign Key)

TABLE: orders
- id (INT, Primary Key, Auto Increment)
- created_at (TIMESTAMP, default: CURRENT_TIMESTAMP)

TABLE: order_items
- id (INT, Primary Key, Auto Increment)
- order_id (INT, Foreign Key)
- product_id (INT, Foreign Key)
- quantity (INT)

TABLE: users (Customers)
- id (INT, Primary Key, Auto Increment)
- full_name (VARCHAR 100)
- email (VARCHAR 100, UNIQUE)
- password (VARCHAR 255, BCrypt hashed)
- loyalty_points (INT, default: 0)
- created_at (TIMESTAMP)

TABLE: producers
- id (INT, Primary Key, Auto Increment)
- full_name (VARCHAR 100)
- email (VARCHAR 100, UNIQUE)
- password (VARCHAR 255, BCrypt hashed)
- company_name (VARCHAR 100)
- status (ENUM: active, inactive, suspended)
- created_at (TIMESTAMP)

TABLE: admins
- id (INT, Primary Key, Auto Increment)
- full_name (VARCHAR 100)
- email (VARCHAR 100, UNIQUE)
- password (VARCHAR 255, BCrypt hashed)
- created_at (TIMESTAMP)

TABLE: loyalty_transactions
- id (INT, Primary Key, Auto Increment)
- user_id (INT, Foreign Key)
- points (INT)
- description (VARCHAR 255)
- created_at (TIMESTAMP)

auth/session.php
  Purpose: Session management and role-based access control
  Key Functions:
    - isLoggedIn(): Returns true if any user type is logged in

    - isProducer(): Returns true if logged in as producer
    - isAdmin(): Returns true if logged in as admin

    - requireProducer(): Restricts to producers only
    - requireAdmin(): Restricts to admins only

    - loginProducer($producerId, $email, $companyName): Creates producer session
    - loginAdmin($adminId, $email): Creates admin session
    - logout(): Destroys session and redirects

auth/login.php
  Purpose: User authentication and login
  Features:
    - Three authentication tabs (Customer/Producer/Admin)
    - Validates email and password
    - Uses password_verify() for BCrypt validation
    - Checks producer status (must be active)
    - Creates session on successful login
    - Displays demo credentials to users
  Authentication Flow:
    1. User selects user type
    2. Enters email and password
    3. System queries appropriate table (users, producers, or admins)
    4. Verifies password with password_verify()
    5. For producers: checks if status == 'active'
    6. Creates session and redirects to dashboard.php

    $result = $stmt->get_result();

    - Password strength checking (min 6 characters)
    - Password confirmation matching
    - BCrypt password hashing
    - Duplicate email detection
    - Producers start as "inactive" (need admin approval)
  Validation:
    - All required fields filled
    - Valid email format
    - Password at least 6 characters
    - Passwords match

API LAYER
---------
api/checkout.php
  Purpose: REST API endpoint for order processing
  Method: POST
  Input Format: JSON
    {
      "cart": [
        {"id": 1, "name": "Product", "price": 99.99, "quantity": 1},
        ...
      ]
    }
  Output Format: JSON
    Success:
      {
        "success": true,
        "message": "Order placed successfully",
        "order_id": 123
      }
    Error:
      {
        "success": false,
        "message": "Error description"
      }
  Features:
    - Validates cart data
    - Uses database transactions for data integrity
    - Creates order header (INSERT INTO orders)
    - Adds each item to order_items (INSERT INTO order_items)
    - Automatic rollback on error
    - Returns JSON response with HTTP status codes
  Key Code:
    $conn->begin_transaction();
    
    $sql = "INSERT INTO orders (created_at) VALUES (NOW())";
    $conn->query($sql);
    $order_id = $conn->insert_id;
    
    $stmt = $conn->prepare("INSERT INTO order_items (order_id, product_id, quantity) VALUES (?, ?, ?)");
    foreach ($cart as $item) {
        $product_id = intval($item['id']);
        $quantity = intval($item['quantity']);
        $stmt->bind_param("iii", $order_id, $product_id, $quantity);
        $stmt->execute();
    }
    
    $conn->commit();
  Error Handling:
    - Try-catch blocks catch exceptions
    - Rollback on error: $conn->rollback()
    - Returns JSON error response
    - HTTP 400 status on error, 200 on success

================================================================================

Login Flow:
-----------

------------------

   - Email not already registered

------------------
- Hashing: BCrypt (PASSWORD_BCRYPT)

5. API ENDPOINTS
================================================================================

Checkout Endpoint
-----------------
URL: /api/checkout.php
Method: POST
Content-Type: application/json

Request Example:
POST /api/checkout.php HTTP/1.1
Content-Type: application/json

{
  "cart": [
    {
      "id": 1,
      "name": "Laptop",
      "price": 999.99,
      "quantity": 1
    },
    {
      "id": 2,
      "name": "Mouse",
      "price": 29.99,
      "quantity": 2
    }
  ]
}

Response - Success (HTTP 200):
{
  "success": true,
  "message": "Order placed successfully",
  "order_id": 42
}

Response - Error (HTTP 400):
{
  "success": false,
  "message": "Cart is empty"
}

Validation:
- Cart must not be empty
- Each item must have id and quantity
- Both values must be integers
- Quantity must be > 0

Database Operations:
1. START TRANSACTION
2. INSERT INTO orders (created_at VALUES NOW()) -> get order_id
3. FOR EACH item IN cart:
     INSERT INTO order_items (order_id, product_id, quantity)
4. COMMIT TRANSACTION
5. ON ERROR: ROLLBACK (undo all inserts)

Called By:
- JavaScript fetch() in js/cart.js (checkout() function)
- When user clicks "Proceed to Checkout" button

7. SECURITY FEATURES
================================================================================

Authentication Security:
- BCrypt password hashing (industry standard)
- password_verify() for secure comparison
- Session-based authentication
- Session start check to prevent multiple sessions
- Automatic logout on inactivity (can be configured)

Authorization Security:
- Role-based access control (RBAC)
- Protected endpoints with require*() functions
- Automatic redirect to login if unauthorized
- Session variable validation before allowing access

Database Security:
- Prepared statements with bound parameters
- Parameterized queries prevent SQL injection
- Example:
  $stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
  $stmt->bind_param("i", $id);  // "i" = integer
  $stmt->execute();
- UNIQUE constraints on emails (prevent duplicates)
- Foreign key constraints (referential integrity)

Input Validation:
- Email validation: filter_var($email, FILTER_VALIDATE_EMAIL)
- Password strength: minimum 6 characters
- Password confirmation: matches before saving
- Trim input: trim($_POST['field'])
- Type casting: intval(), floatval() for numbers
- HTML escaping: htmlspecialchars() in display

Data Protection:
- Database transactions for order processing
- Automatic rollback on error (no partial orders)
- Timestamps for audit trail
- Transaction logging (loyalty_transactions table)

Producer Status Control:
- Producers start as "inactive" (need approval)
- Admin can suspend producers
- Suspended producers cannot login
- Status checked during login attempt

Row-Level Security:
- Producers see only their own products
- WHERE producer_id = $current_producer_id in queries
- Orders filtered by producer's products
- Prevents data leakage across producers


8. DATA FLOW EXAMPLES
================================================================================

User Registration Flow:
-----------------------
1. Customer visits register.php
2. User selects "Customer" tab
3. Fills form: Name, Email, Password, Confirm
4. Form submitted via POST

Backend Processing:
- Validate all fields filled
- Validate email format
- Validate password length (>= 6)
- Validate passwords match
- Hash password: password_hash($password, PASSWORD_BCRYPT)
- Check for duplicate email (try INSERT)
- On success:
  * INSERT INTO users (full_name, email, password)
  * Display success message
  * Link to login.php
- On error:
  * Display error message
  * Keep form data

Producer Registration Flow:
----------------------------
1. User visits register.php
2. User selects "Producer" tab
3. Fills form: Name, Email, Company, Password
4. Form submitted via POST

Backend Processing:
- Same validation as customer
- Additional: Require company_name
- Hash password
- Check for duplicate email
- INSERT INTO producers (full_name, email, password, company_name, status='inactive')
- Display message: "Awaiting admin approval"
- Redirect to login after admin approves

Checkout Flow:
--------------
1. Customer adds items to cart (client-side storage)
2. Customer clicks "Proceed to Checkout"
3. JavaScript fetches product list from localStorage
4. JavaScript sends JSON POST to api/checkout.php
5. curl -X POST http://localhost/api/checkout.php \
      -H "Content-Type: application/json" \
      -d '{"cart": [{"id": 1, "quantity": 1}]}'

Backend Processing (api/checkout.php):
- Receive JSON data
- Decode: $data = json_decode(file_get_contents("php://input"), true)
- Validate cart not empty
- Validate each item has id and quantity
- START TRANSACTION
- INSERT INTO orders (created_at VALUES NOW())
- Get order_id: $order_id = $conn->insert_id
- PREPARE: "INSERT INTO order_items (order_id, product_id, quantity) VALUES (?, ?, ?)"
- FOR EACH item in cart:
  * Bind parameters: $stmt->bind_param("iii", $order_id, $product_id, $quantity)
  * Execute: $stmt->execute()
- COMMIT TRANSACTION
- Return JSON: {"success": true, "order_id": 42}

Client Response (js/cart.js):
- Clear cart from localStorage: localStorage.removeItem(CART_STORAGE_KEY)
- Display success message
- Redirect to order confirmation

Login Flow:
-----------
1. User visits auth/login.php
2. User selects user type (Customer/Producer/Admin)
3. Enters email and password
4. Form submitted via POST

Backend Processing:
- Validate fields not empty
- Based on user_type:
  Customer:
    PREPARE: "SELECT id, full_name, email, password FROM users WHERE email = ?"
    BIND: email parameter
    EXECUTE query
    IF result found:
      VERIFY password: password_verify($password, $user['password'])
      IF valid:
        Create session: loginCustomer($id, $email)
        REDIRECT to dashboards/dashboard.php
      ELSE:
        Display: "Invalid email or password"
    ELSE:
      Display: "Invalid email or password"
  
  Producer:
    PREPARE: "SELECT ... FROM producers WHERE email = ?"
    (same as customer, plus CHECK status == 'active')
    IF status != 'active':
      Display: "Your account has been [status] by an administrator"
    ELSE:
      loginProducer($id, $email, $company_name)
      REDIRECT
  
  Admin:
    PREPARE: "SELECT ... FROM admins WHERE email = ?"
    (same verification as customer)
    loginAdmin($id, $email)
    REDIRECT

Dashboard Routing:
- dashboard.php checks getUserType()
- Routes to appropriate dashboard:
  * customer -> customer_dashboard.php
  * producer -> producer_dashboard.php
  * admin -> admin_dashboard.php

Product Edit Flow (Producer):
------------------------------
1. Producer visits producer_dashboard.php
2. Clicks "Edit" on product
3. Modal dialog opens with product details
4. Producer edits: name, price, stock
5. Clicks "Save Changes"
6. Form submitted via POST with action='update_product'

Backend Processing:
- Check REQUEST_METHOD == 'POST'
- Check action == 'update_product'
- Get parameters: product_id, name, price, stock
- Validate owner: WHERE id = ? AND producer_id = ?
- PREPARE: "UPDATE products SET name = ?, price = ?, stock = ? WHERE id = ? AND producer_id = ?"
- BIND: (s = string, d = double, i = integer)
  $stmt->bind_param("sdiii", $name, $price, $stock, $productId, $producerId)
- EXECUTE
- Display success/error message
- Stay on same page showing updated info

Admin Producer Approval Flow:
------------------------------
1. Admin visits admin_dashboard.php
2. Sees producer card with status = 'inactive'
3. Clicks "Approve" button
4. Form submitted via POST with action='update_status'

Backend Processing:
- Check REQUEST_METHOD == 'POST'
- Check action == 'update_status'
- Get: producer_id, new_status
- Validate status in array ['active', 'inactive', 'suspended']
- PREPARE: "UPDATE producers SET status = ? WHERE id = ?"
- BIND: status (string), producer_id (integer)
- EXECUTE
- Display success message
- Page shows updated status

Now producer can login!

KEY SECURITY BEST PRACTICES IMPLEMENTED
================================================================================

1. Password Security
   - BCrypt hashing (password_hash with PASSWORD_BCRYPT)
   - Never stored in plain text
   - Strong verification with password_verify()

2. SQL Injection Prevention
   - All queries use prepared statements
   - Parameters bound with appropriate types ("i", "s", "d")
   - Never concatenate user input into queries

3. Session Security
   - Session IDs generated by PHP
   - Session data stored server-side
   - Session variables validated before use
   - Session destroyed on logout

4. CSRF Protection (Can be added)
   - Token-based validation
   - Regenerate session ID after login

5. Data Validation
   - Email format validation
   - Number type validation and casting
   - Required field checking
   - Enum validation for status values

6. Access Control
   - Role-based authorization checks
   - Automatic redirect to login
   - Row-level security (producers see only own data)
   - Admin-only functions protected

7. Data Integrity
   - Foreign key constraints
   - UNIQUE constraints on emails
   - Database transactions for multi-step operations
   - Automatic rollback on error

8. Error Handling
   - Try-catch blocks for exceptions
   - Generic error messages to users
   - Detailed errors in logs (not displayed)
   - Validation before database operations
